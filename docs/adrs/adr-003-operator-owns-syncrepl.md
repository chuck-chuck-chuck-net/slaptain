# ADR-003: Operator Owns All Syncrepl Configuration

**Status:** Accepted
**Date:** 2026-03-13

## Context

In-cluster N-way multi-master replication (Phase 2) is fully working. Syncrepl stanzas are
generated by the init container at first boot and baked into cn=config via `slaptest`. The
operator manages cn=config for ACLs (ADR-002) and schemas but does not yet touch syncrepl.

Phase 3 adds cross-cluster replication: two or more SlapdClusters in separate Kubernetes
clusters peer with each other via `spec.replication.externalPeers`. This requires the operator
to own **all** syncrepl configuration (in-cluster + external) at runtime, because:

1. Existing pods won't re-run the init container when externalPeers are added to the spec.
2. cn=config is node-local — each pod needs its own syncrepl stanzas.
3. Having a single source of truth (operator) for syncrepl avoids drift between init-generated
   and operator-generated stanzas.

## Options Considered

### A — Init Container Generates Syncrepl; Operator Only Adds External Peers

The init container continues to generate in-cluster syncrepl stanzas at boot. The operator
appends additional syncrepl stanzas for external peers at runtime.

**Rejected because:**
- Two sources of truth for the same attribute (`olcSyncRepl`). The operator must understand
  what the init container generated and avoid conflicting with it.
- `Replace: olcSyncRepl` is atomic — you cannot append to it, you must replace the entire
  set. This means the operator must reconstruct the full set anyway.
- Init-generated stanzas use pod-local ordinal for self-skip. If the operator replaces
  `olcSyncRepl` later (e.g. to add an external peer), it must recreate the self-skip logic,
  duplicating the init container's work.

### B — Operator Owns All Syncrepl (chosen)

The init container generates the replication infrastructure (accesslog DB, syncprov overlay)
but no `syncrepl` stanzas or `mirrormode` declaration. The operator is the sole owner of
`olcSyncRepl` and `olcMirrorMode` in cn=config.

**Accepted because:**
- Single source of truth for all replication topology.
- External peers can be added/removed without pod restarts.
- Clean separation: init container sets up the plumbing, operator wires the peers.
- Consistent with the existing pattern (ADR-002): operator manages cn=config, init container
  provides sensible defaults.

## Decision

The operator is the sole owner of `olcSyncRepl` and `olcMirrorMode` on every RW pod's data
database cn=config entry. The init container (`bootstrap.sh`) generates:
- Global config, TLS, modules
- Accesslog database + syncprov overlay on accesslog DB (RW only)
- Overlay accesslog + syncprov on data DB (RW only)
- Default ACLs

But **not**: `syncrepl rid=...` stanzas or `mirrormode on`.

### RID Scheme

- **In-cluster peers**: RID 1..N (skip self). For pod ordinal `i`, the RID is `i+1`.
  Pod-0 gets stanzas with RIDs 2, 3 (pointing to pod-1, pod-2). Pod-1 gets RIDs 1, 3, etc.
- **External peers**: RID 101..100+M. The first external peer gets RID 101, the second 102, etc.
- This provides clear namespace separation with no collision risk for up to 99 in-cluster replicas.

### Reconciliation

New step `reconcileReplication` (step 7b) runs after `reconcileSchemas` (step 7a). For each
RW pod:
1. Connect via headless DNS, bind as `cn=admin,cn=config`.
2. Find the data DB entry via `findDataDBDN()`.
3. Read current `olcSyncRepl` and `olcMirrorMode`.
4. Compute desired stanzas via `buildDesiredSyncRepl()`.
5. If current != desired: `Modify` → `Replace olcSyncRepl` + `Replace olcMirrorMode`.

Comparison is RID-based and order-insensitive: parse RID from each stanza, compare sets by RID.

## Consequences

- **~10s replication gap on pod restart**: After a pod restarts, it serves stale reads until
  the operator applies syncrepl stanzas on the next reconcile. This is acceptable: slapd serves
  read queries, the operator's 10s requeue interval limits the gap.
- **Init container no longer generates syncrepl**: The `for (( i=0; ... ))` loop and
  `mirrormode on` declaration are removed from `bootstrap.sh`.
- **Syncprov overlay with no consumers is harmless**: The init container still generates the
  syncprov overlay on the data DB. With no syncrepl consumers configured, it is a no-op.
- **External peers can be added/removed at runtime**: Changing `spec.replication.externalPeers`
  triggers a reconcile; the operator recomputes the full syncrepl set and patches cn=config.
- **Read-only replicas**: RO pods do not participate in external peering. The operator applies
  syncrepl to RO pods for in-cluster RW masters only (same as Phase 2).

## Amendment (2026-04-19): Multi-Database RID Scheme

With multiple `SlapdDatabase` CRs per cluster (ADR-004), each database needs its own set of
syncrepl stanzas with non-colliding RIDs. The original RID scheme (1..N in-cluster, 101+
external) assumed a single data database.

### Updated RID Scheme

Each `SlapdDatabase` declares a `spec.replication.ridBase` (integer). The operator computes
per-stanza RIDs as:

- **In-cluster peer `i`**: `ridBase + i + 1`
- **External peer `j`**: `ridBase + 50 + j + 1`

This provides 49 slots for in-cluster peers and 49 slots for external peers per database,
with the `ridBase` providing namespace separation between databases.

Example (3 databases, 3 pods, 2 external peers):

| Database | ridBase | In-cluster RIDs | External RIDs |
|---|---|---|---|
| users | 100 | 101, 102, 103 | 151, 152 |
| mgmt | 200 | 201, 202, 203 | 251, 252 |
| signing | 300 | 301, 302, 303 | 351, 352 |

The `ridBase` is user-provided, not auto-assigned. The operator validates that no two
`SlapdDatabase` CRs in the same cluster have overlapping RID ranges.

### Multi-Database reconcileReplication

`reconcileReplication` changes from operating on a single database (found via `findDataDBDN()`)
to iterating over all `SlapdDatabase` CRs referencing the cluster. For each database on each
pod, it:

1. Finds the `olcDatabase` entry matching the database's suffix.
2. Computes desired syncrepl stanzas using the database's `ridBase`.
3. Compares and replaces if different (same pattern as before).

The global replication settings (keepalive, retry, externalPeers) still come from the
`SlapdCluster` CR. Per-database settings (deltaSync, checkpoint, purge) come from the
`SlapdDatabase` CR. The operator combines both when building stanzas.
