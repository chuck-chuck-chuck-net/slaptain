# ADR-009: SlapdUser Lifecycle

**Status:** Proposed
**Date:** 2026-05-04

## Context

Production OpenLDAP deployments rely on a fixed set of *service users* — bind DNs that
applications use to query or modify the directory: `cn=syncuser`, `cn=dovecot`,
`cn=postfix`, `cn=app1`, `cn=app2`, `cn=emailBackup`, `cn=console`,
`cn=dkimservice`, plus per-DB equivalents.

Today, slaptain creates exactly one such user automatically: `cn=replication,<suffix>`,
generated by the SlapdDatabase controller for syncrepl bind. Everything else — users,
their objectClasses, their userPassword, and the application-side passwords — is the
deployer's responsibility, with no declarative path.

For a slaptain deployment to replace a legacy directory we need a CRD that:

1. Creates these service users declaratively, with auto-generated or
   externally-managed passwords.
2. Survives operator restarts without re-creating or rotating credentials.
3. Lets ACLs on `SlapdDatabase` reference these DNs without ordering races.
4. Does not require a Helm Job, kubectl-exec, or sidecar — consistent with the
   credential architecture in CLAUDE.md and ADR-002.

The operator already creates arbitrary data entries via `applySeedData()` in
`slapddatabase_controller.go:797`. SlapdUser is the structurally-correct wrapper:
proper CR ownership, status, and password lifecycle.

## Scope

**In scope:**

- Service users — bind DNs used by applications or the operator itself.
- Standard objectClasses (`organizationalRole`, `simpleSecurityObject`,
  `inetOrgPerson`, etc.) and arbitrary attribute maps.
- Password lifecycle: auto-generate on first reconcile, or read from an existing Secret.
- DN composition under a parent in the data tree.

**Out of scope:**

- General end-user provisioning (millions of mailbox users). That data lives in
  application bulk-load tooling, not a CR.
- Group membership graphs, role hierarchies, dynamic groups.
- DN renames (`modrdn`). Service-user DNs are stable by convention.
- Schema management — `objectClasses` referenced here must already exist (via base
  schemas or SlapdSchema CRs).

## Options Considered

### Option A: Helm Job + bootstrap script (rejected)

A Helm post-install Job that runs `ldapadd` from a configmapped LDIF, gated on slapd
being ready.

**Rejected.** Helm Jobs do not fit slaptain's CI/CD model (we don't use them for
anything else), they have no ongoing reconciliation (drift not detected), and they
don't compose with ACL declarations on SlapdDatabase.

### Option B: SlapdUser CR, per-pod write (rejected)

Mirror SlapdSchema and SlapdDatabase ACLs: connect to every pod via headless DNS and
add the entry on each.

**Rejected.** Unlike `cn=config` (which is node-local — ADR-002), the data tree is
**replicated**. Writing the same entry on N pods produces N independent change records,
which syncrepl then has to converge. Best case: wasted work and noisy CSN advancement.
Worst case: same-DN add races between pods produce conflicting CSNs and require
manual resolution.

### Option C: SlapdUser CR, single-pod write (chosen)

Connect to one pod, add or modify the entry there, let syncrepl propagate to peers.

**Chosen.** This is how application code writes to a multi-master LDAP cluster. The
operator should behave the same way. Convergence is observable via existing CSN
monitoring (ADR-008), so we get drift detection for free at the cluster level.

## Decision

A new CRD `SlapdUser` (group `ldap.chuck-chuck-chuck.net`, version `v1alpha1`,
short name `su`) declares a service user in the data tree of a SlapdDatabase. The
controller writes to a single pod and lets syncrepl propagate.

### CRD shape

```yaml
apiVersion: ldap.chuck-chuck-chuck.net/v1alpha1
kind: SlapdUser
metadata:
  name: dovecot
spec:
  databaseRef: example           # SlapdDatabase name (required, immutable)
  parentDN: "ou=config"       # appended to suffix, optional (default: suffix root)
  cn: dovecot                 # forms cn=dovecot,ou=config,<suffix> (required, immutable)
  objectClasses:              # required, immutable
    - organizationalRole
    - simpleSecurityObject
  attributes:                 # mutable; map of name → list of values
    description: ["Dovecot LDAP bind user"]
  password:
    secretRef:                # optional: read userPassword from this Secret
      name: dovecot-password
      key: password
    autoGenerateLength: 32    # used only when secretRef is unset; default 32
  deletionPolicy: Retain      # Retain (default) | Delete
  adoptExisting: false        # default false; true allows takeover of an unmanaged entry
status:
  phase: Pending|Running|Conflict|Error
  observedDN: "cn=dovecot,ou=config,o=example"
  generatedSecretName: ""     # set when password was auto-generated
  conditions:
    - type: Ready
    - type: PasswordSync      # last password sync time
```

### Write target

The controller picks the **lowest-ordinal Ready RW pod** of the target SlapdCluster
(via the headless service DNS) and connects there. If unavailable, the next ordinal.
If all RW pods are unavailable, the reconcile is requeued; no fallback to RO pods
(they reject writes).

The controller binds as the data admin (`<suffix>` rootDN) using
`<dbname>-credentials` / `root-password` — the same credential the SlapdDatabase
controller uses for ACL management.

### Add semantics

Idempotent. The controller searches for the computed DN before adding. If it exists:

- If the entry has the SlapdUser's owner annotation (or `adoptExisting: true`),
  compare attributes and `ldap_modify` if differences.
- Otherwise, set `phase: Conflict` with a message naming the existing DN. Do not
  overwrite. The operator surfaces this state and waits for human intervention.

The owner annotation is implemented via a structural attribute we control. To avoid
schema sprawl, we use `description` with a stable prefix like
`description: "managed-by:slaptain:slapduser:<namespace>/<name>"`, included by the
controller alongside any user-supplied `description` values.

### Update semantics

- `attributes`: mutable. Diff against current entry; `ldap_modify` to add/replace/delete
  attribute values.
- `password.secretRef`: mutable. Whenever the referenced Secret's resource version
  changes (or the controller observes a different value), `ldap_modify` updates
  `userPassword`. slapd hashes with `{SSHA}` automatically.
- `cn`, `parentDN`, `databaseRef`, `objectClasses`: **immutable**. The validating
  webhook rejects changes; if changes slip through (no webhook installed), the
  controller surfaces an Error condition without acting. Renaming requires deleting
  and re-creating the SlapdUser CR.

### Delete semantics

Mirrors ADR-005 (SlapdDatabase cleanup policy):

- **Retain** (default): the operator removes its finalizer; the directory entry is
  preserved. Service users typically outlive their CRs (mid-flight rotation, lab
  cleanup, etc.).
- **Delete**: the controller issues `ldap_delete` on the entry, then removes the
  finalizer. If the entry is not found, treat as success.

In **Delete** mode, an auto-generated `<name>-credentials` Secret is also deleted
(operator owner reference). With `secretRef`, the referenced Secret is left alone
(deployer-owned).

### Password lifecycle

Two paths, mutually exclusive:

| `password.secretRef` set | Behavior |
|---|---|
| Yes | Operator reads the Secret; on each reconcile, compares hash of current value to last applied (cached in status) and `ldap_modify` if different. Never modifies the Secret. |
| No | Operator generates a random `autoGenerateLength`-character password on first reconcile, stores it in `<name>-credentials` Secret (key `password`), and writes it to LDAP. On subsequent reconciles, reads the Secret and re-applies if needed (idempotent). Never regenerates without explicit user action. |

Operators that want to rotate an auto-generated password: edit the
`<name>-credentials` Secret; the controller picks up the change.

### Reconcile order

SlapdUser reconciliation depends on the referenced SlapdDatabase being in
`phase: Running`. If not, the controller requeues. This avoids races during cluster
bootstrap (the SlapdDatabase controller creates the data DB and root entries; only
then can SlapdUser entries be added).

### What this does NOT manage

- ACLs that grant the user access. Those go on `SlapdDatabase.spec.acls` and reference
  the user's DN. The two CRs are decoupled by design: SlapdDatabase ACLs need the user
  DN to *exist as a string*, not necessarily as a directory entry, when the ACL is
  applied. This avoids cyclic ordering between SlapdDatabase and SlapdUser.

## Consequences

- **Single source of truth for service users.** A new application bind user is one
  CR, one Secret reference (or zero, with auto-gen), and an ACL line on the
  corresponding SlapdDatabase.
- **Drift correction.** Manual edits to a SlapdUser-owned entry are reverted on the
  next reconcile (attribute mismatch ⇒ `ldap_modify`). Conflicts with an existing,
  unowned entry surface in status rather than being silently overwritten.
- **No per-pod fan-out.** Slaptain assumes data-tree replication is healthy; if a pod
  is partitioned, its copy will catch up via syncrepl rather than being directly
  written. Failing pods don't block SlapdUser reconciliation as long as one RW pod is
  reachable.
- **Pod selection is best-effort.** The lowest-ordinal Ready pod might not be the
  same on every reconcile, but writes are idempotent so this is harmless.
- **Bootstrap ordering matters.** Service users referenced by ACLs must exist before
  applications attempt to bind. The reconcile ordering (SlapdDatabase → SlapdUser →
  application clients) is handled by the user's GitOps tooling; the operator does
  not enforce a global apply order.
- **Schema is not validated up front.** If `objectClasses` references a class not
  loaded on the cluster (missing SlapdSchema), the `ldap_add` fails with
  `objectClassViolation` and the controller surfaces an Error. This is acceptable
  feedback; failing earlier (in a webhook that introspects loaded schemas) adds
  complexity without eliminating the failure mode.
